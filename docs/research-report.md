# Scripted RhinoCommon lets agents draw NURBS

> **About this document.** This report was researched and written by Claude (Anthropic) research agents on 23 November 2026 as background for the `rhino-nurbs-drawings` and `rhino-nurbs-modelling` skills. It was written when both were one skill that modelled in 3D and derived drawings from the model; the drawing skill has since been rewritten to draw directly in 2D. It has not been reviewed line by line by a person. Benchmark figures were extracted from the cited papers by an automated reader and should be checked against the sources before reuse. Items marked "Unverified", "Inference" or "Source conflict" are flagged as such in the text. The addendum at the end records checks made afterwards in a live Rhino 9 session, which settle several of the open items.

As of November 2026, the most dependable way to get Claude Code past circles and cubes is to stop routing geometry through typed MCP tools and have the agent write and run RhinoCommon Python scripts in a live Rhino 8 session. Two routes do this on Windows: McNeel's official script-first MCP server (Package Manager name `Rhino-MCP-Platform`) and the `rhinocode` command line tool, which needs no MCP server. The primitive-only symptom matches how community servers are built: the most used one, `rhinomcp`, offers a `create_object` tool whose type list ends at lines, arcs, simple curves, boxes, spheres, cones, cylinders and point-grid surfaces. RhinoCommon covers the whole drawing pipeline: explicit NURBS curves and blends, lofts, sweeps and network surfaces, plane sections with hatches, the `HiddenLineDrawing` class behind Make2D, and vector PDF, SVG and DWG export. Without Rhino, build123d with ezdxf was the one headless stack in this research that kept true spline curves from model to DXF and SVG. Research on agent-written CAD supports a specific method: executable code, a written decomposition, a cheat sheet of verified API calls, short scripts run one at a time, numeric checks as the main gate, rendered views as a secondary check, and two to three repair rounds. Three limits apply. Most frontier models still produced invalid output on 68% to 92% of loft, sweep and shell tasks in a May 2026 benchmark. No located study evaluates agents on detailed architectural plans or sections. None of the Rhino code patterns collected here was executed in Rhino during the research, so a skill built on them needs a first verification pass.

## A typed primitive tool sets the ceiling, and script-first routes remove it

### The symptom matches the tool list of community servers

No maintainer statement explaining primitive-only output was found, so the diagnosis rests on tool lists. The most widely used community server, jingcheng-chen's `rhinomcp` (version 0.5.1, released 7 November 2026), exposes a `create_object` tool with these types: POINT, LINE, POLYLINE, CIRCLE, ARC, ELLIPSE, CURVE (interpolated or control-point), BOX, SPHERE, CONE, CYLINDER and SURFACE from a point grid ([rhinomcp implementation notes](https://cdn.jsdelivr.net/gh/jingcheng-chen/rhinomcp@main/docs/IMPLEMENTATION.md); [PyPI rhinomcp](https://pypi.org/project/rhinomcp/)). Anything richer needs the separate `loft`, `sweep1`, `extrude_curve`, `pipe` and boolean tools, or the script executors `execute_rhinoscript_python_code` and `execute_rhinocommon_csharp_code` ([rhinomcp README](https://cdn.jsdelivr.net/gh/jingcheng-chen/rhinomcp@main/README.md)). The server's environment variables can switch the script tools off, and no documented variable switches the primitive tool off ([rhinomcp README](https://cdn.jsdelivr.net/gh/jingcheng-chen/rhinomcp@main/README.md)). `rhinoclaw` shares the same port and tool names ([PyPI rhinoclaw](https://pypi.org/project/rhinoclaw/)).

**Inference, not stated by any source:** when a cheap typed tool sits beside an open-ended script tool, a loosely worded request maps onto the typed tool, and the result is primitives. Benchmark data points the same way. In P3D-Bench (June 2026), the strongest model scored about 0.8 on a semantic judge and about 0.35 on a geometry judge, and in Text2CAD-Bench (May 2026) invalid output rose sharply once tasks required sweeps, lofts and shells ([P3D-Bench](https://arxiv.org/html/2606.11152v2); [Text2CAD-Bench](https://arxiv.org/html/2605.18430v1)). A model left to choose stays with the operations it executes reliably.

McNeel's official server is designed the other way round. Callum Sykes of McNeel announced it on 7 May 2026 and explained that, because Claude prefers writing Python, the server runs Python or Rhino commands; he also named low-token-first behaviour as an area still needing work ([McNeel forum, Rhino MCP Server](https://discourse.mcneel.com/t/rhino-mcp-server/216568)). Since 30 September 2026 it ships inside the Rhino 9 BETA as RhinoAI, and Rhino 8 users install it from the Package Manager, where it keeps the listing name `Rhino-MCP-Platform` ([RhinoAI beta thread](https://discourse.mcneel.com/t/rhino-beta-feature-rhinoai/223146.md)). Its scripting tools are `run_python`, `run_csharp` and `run_command` ([DeepWiki scripting tools, secondary](https://deepwiki.com/mcneel/RhinoMCP/3.2-scripting-tools:-run_python-run_csharp-run_command)). **Inference:** the secondary tool lists show no typed geometry-creation tools, so the agent has no box tool to fall back on.

User reports show that the script-first design reaches NURBS work, with uneven quality. One forum user gave Claude a partial Ferrari P4 model through this server on 1 October 2026 and watched about 35 minutes of modelling in which every missing part came out as NURBS; the user found plenty to correct and ran out of credits ([McNeel forum, first try](https://discourse.mcneel.com/t/rhino-mcp-claude-first-try/223183)). Another user reported a very poor result from a "build me a stadium" request on first install ([McNeel forum, page 4](https://discourse.mcneel.com/t/rhino-mcp-server/216568?page=4)). One blog author judges, without measurement, that freeform surfacing where continuity matters remains weak ([techdrawai](https://techdrawai.com/blog/connect-claude-to-rhino)).

### Two live-Rhino routes suit Claude Code on Windows

The first route is the McNeel server. The official steps are: install Claude Code, install `Rhino-MCP-Platform` from the Package Manager in Rhino 8 or the Rhino 9 WIP/BETA, run the `MCPConnect` command in Rhino, and paste the prompt it provides into a new Claude Code session ([RhinoAI Claude Code guide](https://mcneel.github.io/RhinoAI/docs/getting-started/cc-plugin/)). The router targets Rhino 8 by default; adding `"args": ["-v", "9"]` under the `rhino` entry in `~/.claude.json` targets Rhino 9 ([RhinoAI troubleshooting](https://mcneel.github.io/RhinoAI/docs/troubleshooting/)). McNeel distinguishes two modes: the `AI` command opens a chat panel inside Rhino, while `MCPConnect` turns Rhino into a tool server for an external client such as Claude Code and adds process control (start, close and restart Rhino, several instances, recovery after a crash) ([RhinoAI versus RhinoMCP post](https://discourse.mcneel.com/t/rhino-beta-feature-rhinoai/223146/5)). A blog that read the plugin code reports 42 tools and a Claude Code plugin containing a `rhino-drafter` agent that uses `run_python` for layouts and dimensions and `run_command` for Make2D; this is a secondary description, and the same blog says McNeel's documentation currently hides that section ([techdrawai](https://techdrawai.com/blog/connect-claude-to-rhino)).

The second route has no MCP layer. `rhinocode` is McNeel's command line utility for Rhino's scripting infrastructure and requires Rhino 8.11 or later; running `StartScriptServer` in Rhino enables it, and on Windows the executable sits in `%PROGRAMFILES%\Rhino 8\System` ([RhinoCode CLI guide](https://developer.rhino3d.com/guides/scripting/advanced-cli)). `rhinocode script C:\path\file.py` runs a script file in the open Rhino, `rhinocode command "_circle 0 0 0 20"` runs a command, and `rhinocode list --json` lists running instances ([RhinoCode CLI guide](https://developer.rhino3d.com/guides/scripting/advanced-cli)). **Unverified:** the guide does not say whether print output or tracebacks return to the terminal. **Inference:** each script should therefore write its results (object ids, counts, measurements, errors) to a JSON file and save a PNG, which Claude Code then reads from disk. The script files stay on disk as a reviewable record, and there is no tool list to bias the agent.

### Reported failures are silent no-ops, engine mismatches and token cost

Several reports describe scripts that did nothing while the tool reported success. A user with a French Rhino interface found that `run_python` and `run_csharp` never executed although `run_command` worked, which McNeel traced to a missing underscore; another found that C# scripts written as a class with a `Main` method were a silent no-op ([McNeel forum, page 3](https://discourse.mcneel.com/t/rhino-mcp-server/216568?page=3)). A secondary reading of the code says `run_python` detects errors by scanning the command history for traceback text, so success is inferred from output ([DeepWiki scripting tools](https://deepwiki.com/mcneel/RhinoMCP/3.2-scripting-tools:-run_python-run_csharp-run_command)). The practical consequence is a mandatory check after every script: object counts or a capture, never the tool's own success message.

Python engine mismatch is the second recurring cause. Under `RunPythonScript`, f-strings work only when the script begins with `#! python3` or is saved as `.py3` ([McNeel forum, f-strings thread, 2025](https://discourse.mcneel.com/t/f-strings-wont-work-with-runpythonscript/199697)). Servers differ: EaseHee describes its Python tool as IronPython, tanishqbhattad separates `execute_script` (IronPython 2) from `execute_python3`, and `rhinomcp` does not state its engine ([EaseHee README](https://github.com/easehee/rhino-mcp); [tanishqbhattad/rhino-mcp](https://github.com/tanishqbhattad/rhino-mcp)). **Source conflict:** two pages of the same secondary source describe McNeel's `run_python` as "Python 3 on the Rhino 8+ ScriptEditor" and as "IronPython 2.7 or CPython 3.x, depending on Rhino version" ([DeepWiki scripting tools](https://deepwiki.com/mcneel/RhinoMCP/3.2-scripting-tools:-run_python-run_csharp-run_command); [DeepWiki tools reference](https://deepwiki.com/mcneel/RhinoMCP/3-mcp-tools-reference)). Forum users report the same problem from the other side: chat models default to Rhino 7 IronPython patterns unless Python 3 is stated explicitly ([McNeel forum, working GH code thread](https://discourse.mcneel.com/t/has-anyone-actually-received-working-grasshopper-code-from-ai/219720)).

Setup problems cluster around the runtime and the instance. The McNeel plugin does not load when Rhino runs its .NET Framework build, on Intel Macs, or on outdated Rhino builds, and one user lost three hours to the router opening Rhino 8 when Rhino 9 was intended ([RhinoAI troubleshooting](https://mcneel.github.io/RhinoAI/docs/troubleshooting/); [McNeel forum, page 2](https://discourse.mcneel.com/t/rhino-mcp-server/216568?page=2)). One Rhino bug matters for drawings: reading `rs.ObjectLayout(obj)` on layout-space objects moved them to model space and a repeat crashed Rhino, logged as RH-96724 ([McNeel forum, page 3](https://discourse.mcneel.com/t/rhino-mcp-server/216568?page=3)). **Source conflict:** a blog says the `rhinomcp` plugin always listens on port 1999, while the README says further instances take 2000 and upward ([techdrawai](https://techdrawai.com/blog/connect-claude-to-rhino); [rhinomcp README](https://cdn.jsdelivr.net/gh/jingcheng-chen/rhinomcp@main/README.md)). Token use is high in every report: one conversation consumed half a daily Claude Pro quota ([McNeel forum, page 1](https://discourse.mcneel.com/t/rhino-mcp-server/216568)).

### Grasshopper and headless Rhino are secondary routes

Grasshopper is now reachable from the McNeel server, from `rhinomcp` (`gh_build_graph` and related tools) and from dedicated servers. lamcp 0.9.0 from Gramazio Kohler Research (19 November 2026) offers 17 tools, among them `add_python_component`, `solve_grasshopper` and `capture_grasshopper_canvas`, and installs with `claude mcp add lamcp --scope user -- uvx lamcp` ([PyPI lamcp](https://pypi.org/project/lamcp/)). Cordyceps began as a way to update C# script components without copy and paste ([Cordyceps thread](https://discourse.mcneel.com/t/cordyceps-mcp-server-for-grasshopper-win-mac/215122)). **Source conflict:** McNeel's Grasshopper 2 tools are prefixed `g2_` in two secondary sources and `gh2_` on the official troubleshooting page, and the Grasshopper 1 solve tool appears as both `g1_solve` and `g1_solve_graph` ([DeepWiki Grasshopper tools](https://deepwiki.com/mcneel/RhinoMCP/3.3-grasshopper-tools-(gh1-and-gh2)); [RhinoAI troubleshooting](https://mcneel.github.io/RhinoAI/docs/troubleshooting/); [McNeel forum, page 4](https://discourse.mcneel.com/t/rhino-mcp-server/216568?page=4)).

Evidence favours text code over wiring native components. A peer-reviewed ACADIA 2024 study that generated Grasshopper definitions with three GPT-4o agents found the exact-name JSON step the weakest element, and its most complex case did not resemble the target ([ACADIA 2024 preprint](https://arxiv.org/html/2411.14485v1)). A forum user needed about 25 attempts before a Python script that writes a `.gh` file worked ([McNeel forum, Can Claude do GH](https://discourse.mcneel.com/t/can-claude-do-gh-part-1-1-1-2-and-1-3/218637)). The positive report, a 655-louvre pavilion, was built in five staged proofs of concept ([McNeel forum, pavilion](https://discourse.mcneel.com/t/a-pavilion-via-an-ai-relay-chatgpt-claude-official-rhinomcp/219153)). **Inference:** for a parametric drawing, placing a Python or C# script component is a more direct agent route than assembling many native components.

Headless Rhino routes are weaker for this task. The `rhinoinside` package for CPython is Windows only, and its three newest PyPI releases are yanked, with 0.7.0 from May 2025 the latest usable one ([PyPI rhinoinside](https://pypi.org/project/rhinoinside)). Rhino.Compute runs RhinoCommon and Grasshopper behind a web server at no extra cost on a licensed Windows PC; McNeel's public server is switched off, so users host their own ([Compute FAQ](https://developer.rhino3d.com/guides/compute/compute-faq/)). rhino3dm reads and writes `.3dm` files without Rhino and defers advanced geometry operations to Compute ([What is rhino3dm](https://developer.rhino3d.com/guides/opennurbs/what-is-rhino3dmio/)).

### The agent sees Rhino through small captures

Every live server has a capture tool: `get_viewport_image` (McNeel), `capture_viewport` (`rhinomcp`), `rhino_screenshot` (EaseHee) and `capture_rhino_viewport` (lamcp) ([DeepWiki tools reference](https://deepwiki.com/mcneel/RhinoMCP/3-mcp-tools-reference); [rhinomcp README](https://cdn.jsdelivr.net/gh/jingcheng-chen/rhinomcp@main/README.md); [PyPI lamcp](https://pypi.org/project/lamcp/)). McNeel's server captures at reduced resolution to save tokens; a blog reading the settings code gives the default as 480 by 270 pixels, which is a secondary figure ([McNeel forum, page 1](https://discourse.mcneel.com/t/rhino-mcp-server/216568); [techdrawai](https://techdrawai.com/blog/connect-claude-to-rhino)). That size is small for reading a section drawing. In a script-only route the agent captures to a file itself with `Rhino.Display.ViewCapture`, setting `Width` and `Height` before `CaptureToBitmap(view)` ([ViewCapture API](https://developer.rhino3d.com/api/rhinocommon/rhino.display.viewcapture)). Some servers already pair images with numeric checks, for example tanishqbhattad's `assert_geometry` for bounding box, object count and watertightness ([tanishqbhattad/rhino-mcp](https://github.com/tanishqbhattad/rhino-mcp)).

## RhinoCommon covers the whole drawing pipeline, with four weak joints

The API facts in this section were read from the official `rhinoscriptsyntax` source (branch `rhino-8.x`), the RhinoCommon API site and McNeel's samples repository. No code was executed in Rhino during the research. Patterns described as assembled combine verified signatures and remain untested. The four weak joints are native Clipping Drawings (no SDK), clipping planes inside the hidden-line API (residual differences from Make2D), export scale (undocumented argument) and exact-scale SVG (no confirmed method).

| Drawing step | Call that exposes the control | Point to encode in a skill |
|---|---|---|
| Explicit NURBS curve | `rs.AddNurbsCurve(points, knots, degree, weights=None)`; `Rhino.Geometry.NurbsCurve(dimension, rational, order, pointCount)` with `Points` and `Knots` | Knot count equals point count plus degree minus 1; order is degree plus 1 |
| Interpolated curve | `rs.AddInterpCurve(points, degree=3, knotstyle=0, start_tangent=None, end_tangent=None)`; `Curve.CreateInterpolatedCurve` | Knot styles 3 to 5 are periodic; tangents are omitted for periodic curves |
| Continuity between curves | `rs.AddBlendCurve(curves, parameters, reverses, continuities)`; `Curve.CreateBlendCurve`; `Curve.CreateMatchCurve` | Continuity 0, 1, 2 means position, tangency, curvature |
| Loft | `Brep.CreateFromLoft`, `CreateFromLoftRebuild`, `CreateFromLoftRefit` | No sorting, direction or seam correction is applied |
| Sweep | `Brep.CreateFromSweep` overloads with frame, blend, miter and rebuild arguments | `rs.AddSweep1` and `rs.AddSweep2` expose only rail, shapes and closed |
| Network surface | `NurbsSurface.CreateNetworkSurface(curves, continuity, edgeTolerance, interiorTolerance, angleTolerance, out error)` | Error codes 1 to 4 name the failure; `rs.AddNetworkSrf` discards them |
| Section cut | `Intersection.BrepPlane(brep, plane, tolerance, out curves, out points)`; `Brep.CreateContourCurves` | A `joinCurves` overload exists from Rhino 8.27 |
| Poché | `Hatch.Create(curves, hatchPatternIndex, rotationRadians, scale, tolerance)`; `Hatch.Create(plane, outerLoop, innerLoops, ...)` | Boundaries must be closed and planar |
| Hidden-line projection | `HiddenLineDrawingParameters`; `HiddenLineDrawing.Compute(parameters, True)` | Sort segments by `SegmentVisibility` and `ParentCurve.SilhouetteType` |
| Line weights | `Layer.PlotWeight` in millimetres; `rs.LayerPrintWidth`; `rs.ObjectPrintWidth` | 0 means default width; a negative value means do not print |
| Vector PDF | `FilePdf.Create()`, `AddPage(ViewCaptureSettings)`, `Write(path)` | `RasterMode = False` and `UsePrintWidths = True` |
| SVG | `ViewCapture.CaptureToSvg(settings)` | Takes a `ViewCaptureSettings`, not a view |
| DWG | `doc.Export(path, FileDwgWriteOptions().ToDictionary())` | Rhino 8 code-driven file IO |
| PNG for review | `ViewCapture.CaptureToBitmap(view)` | Set `Width` and `Height` first |

### Three curve functions expose real control

Most `rhinoscriptsyntax` curve functions are thin wrappers, and only three give control over the curve definition. `rs.AddNurbsCurve` takes an explicit knot vector, degree and optional weights. `rs.AddInterpCurve` takes degree, one of six knot styles and end tangents. `rs.AddBlendCurve` takes a continuity value per end ([rhinoscriptsyntax curve.py](https://github.com/mcneel/rhinoscriptsyntax/blob/rhino-8.x/Scripts/rhinoscript/curve.py)). By contrast, `rs.AddCurve` produces a clamped uniform curve with unit weights. For rational control points, end conditions and bulge, a script works on `Rhino.Geometry.NurbsCurve` directly: `nc.Points[i] = ControlPoint(pt, weight)`, `nc.Knots[i]`, `SetEndCondition`, `CreateHSpline`, and the `Curve.CreateBlendCurve(curveA, curveB, continuity, bulgeA, bulgeB)` overload ([NurbsCurve API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.nurbscurve); [Curve API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.curve)). McNeel's `SampleNurbsCurves.py` builds a rational cubic by hand with four points and six knots and is a suitable verified example for a cheat sheet ([SampleNurbsCurves.py](https://github.com/mcneel/rhino-developer-samples/blob/9/rhinopython/SampleNurbsCurves.py)).

Several wrappers behave differently from what their names or docstrings suggest, which is the material a gotchas list should hold. `rs.CloseCurve` documents the absolute tolerance as its default, yet its code substitutes `RhinoMath.ZeroTolerance`. `rs.RebuildCurve` hard-codes `preserveTangents` to False. `rs.AddFilletCurve` adds only the arc and leaves the input curves untrimmed. `rs.JoinCurves` defaults to 2.1 times the document tolerance. `rs.OffsetCurve` returns a list because one offset can yield several curves ([rhinoscriptsyntax curve.py](https://github.com/mcneel/rhinoscriptsyntax/blob/rhino-8.x/Scripts/rhinoscript/curve.py)).

### Lofts fail on order, direction and seams, and wrappers hide the reasons

The docstring of `rs.AddLoftSrf` states the three known failure causes: curves are not sorted, open-curve directions are not adjusted, and closed-curve seams are not adjusted ([rhinoscriptsyntax surface.py](https://github.com/mcneel/rhinoscriptsyntax/blob/rhino-8.x/Scripts/rhinoscript/surface.py)). An assembled pre-flight follows from that: compare consecutive open curves with `Curve.DoDirectionsMatch` and reverse where needed, align closed-curve seams with `ChangeClosedCurveSeam(t)`, and optionally rebuild all sections to one degree and point count before calling `Brep.CreateFromLoft`. McNeel's `SampleCreateFromLoftRebuild.py` shows the calling convention: a typed array `System.Array[Rhino.Geometry.Curve]([...])` and `Point3d.Unset` for the optional end points ([SampleCreateFromLoftRebuild.py](https://github.com/mcneel/rhino-developer-samples/blob/9/rhinopython/SampleCreateFromLoftRebuild.py)).

Other surface wrappers drop information. `rs.AddNetworkSrf` returns None without the error code that `NurbsSurface.CreateNetworkSurface` provides. `rs.AddPatch` treats its second argument as span counts only when it is a tuple such as `(10, 10)`. `rs.OffsetSurface` rejects any brep with more than one face. The boolean wrappers delete their inputs by default ([rhinoscriptsyntax surface.py](https://github.com/mcneel/rhinoscriptsyntax/blob/rhino-8.x/Scripts/rhinoscript/surface.py); [NurbsSurface API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.nurbssurface)). For booleans, Rhino 8 added a `Brep.CreateBooleanUnion` overload that returns naked-edge, bad-intersection and non-manifold points, which gives an agent the location of a failure ([Brep API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.brep)). SubD is scriptable through `SubD.CreateFromLoft`, `CreateFromSweep`, `CreateFromMesh` and `ToBrep()` ([SubD API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.subd)).

### Sections work through intersection and hatch calls, while Clipping Drawings have no SDK

A scripted section uses `Intersection.BrepPlane` for one cut or `Brep.CreateContourCurves` for a series, then `Curve.JoinCurves` to close loops, then `Hatch.Create` for the poché, with `doc.Objects.AddCurve(curve, attributes)` and `AddHatch(hatch, attributes)` placing results on a cut layer ([Intersection API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.intersect.intersection); [Hatch API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.hatch); [ObjectTable API](https://developer.rhino3d.com/api/rhinocommon/rhino.docobjects.tables.objecttable)). **Unverified:** whether passing nested closed loops to one `Hatch.Create(IEnumerable<Curve>, ...)` call yields holes is not stated in the API text; the overload with explicit `outerLoop` and `innerLoops` (since Rhino 7.18) avoids the question. **Inference:** open section loops mean the source brep is not solid at the cut, so the script should test `IsSolid` and try `CapPlanarHoles` before cutting.

Rhino 8's native section system is command-driven. `ClippingDrawings` extracts section curves, hatches, background silhouettes and hidden curves into 2D drawings, and related commands export and update them ([Rhino 8 help, ClippingPlane](https://docs.mcneel.com/rhino/8/help/en-us/commands/clippingplane.htm)). McNeel staff said in April 2025 that no SDK is exposed to extract clipping drawings, and a question in August 2026 about Rhino 9 had no answer when read ([McNeel forum 215310](https://discourse.mcneel.com/t/clipping-drawings-in-grasshopper-and-api-access-in-r8-r9-any-updates/215310)). The scriptable parts are `ObjectTable.AddClippingPlane` and the `SectionStyle` class on layers (since Rhino 8.0) ([SectionStyle API](https://developer.rhino3d.com/api/rhinocommon/rhino.docobjects.sectionstyle)). **Unverified:** the dash-command option order for `-ClippingDrawings` and `-Make2D` is not documented on the help pages and would have to be discovered interactively.

### HiddenLineDrawing is the scriptable Make2D

`Rhino.Geometry.HiddenLineDrawing` is the API behind Make2D. A script fills a `HiddenLineDrawingParameters` object (`AbsoluteTolerance`, `Flatten`, `IncludeHiddenCurves`, `IncludeTangentEdges`, `SetViewport`, `AddGeometry`), calls `HiddenLineDrawing.Compute(parameters, True)`, and iterates `hld.Segments` ([HiddenLineDrawingParameters API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.hiddenlinedrawingparameters); [HiddenLineDrawing API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.hiddenlinedrawing)). Each segment carries a visibility value (Visible, Hidden, Duplicate, Projecting, Clipped), an `IsSceneSilhouette` flag and a parent curve whose `SilhouetteType` distinguishes Tangent, Crease, Boundary and SectionCut ([Visibility enum](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.hiddenlinedrawingsegment.visibility); [SilhouetteType enum](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.silhouettetype)). McNeel's Python 3 sample `SampleMake2dSnapshots.py` is a complete worked example that routes scene silhouettes and other visible curves to separate layers with their own plot weights ([SampleMake2dSnapshots.py](https://github.com/mcneel/rhino-developer-samples/blob/9/rhinopython/SampleMake2dSnapshots.py)). That gives an agent a direct mapping from segment class to layer: section cut, outline, edges, light edges, hidden.

Clipping planes inside this API are the fragile part. Rajaa Issa of McNeel explained in February 2026 that a clipping plane must be flipped before `AddClippingPlane` registers it, and in 2024 that cut geometry must be added with `AddGeometryAndPlanes`; the user then got section cuts but still saw dropped and extra segments compared with native Make2D, which stayed unresolved ([McNeel forum 215626](https://discourse.mcneel.com/t/hiddenlinedrawing-clipping-planes-are-ignored-in-make2d-calculation-c/215626); [McNeel forum 178984](https://discourse.mcneel.com/t/rhino-8-hiddenlinedrawing-issue-with-occludingsectionoption/178984)). **Inference (assembled, not executed):** a more robust section drawing takes the cut linework and hatches from `Intersection.BrepPlane`, and the view beyond from a hidden-line run on geometry already trimmed with `Brep.Trim(plane, tolerance)` and capped, so no clipping plane enters the hidden-line computation. Make2D also omits intersection lines between interpenetrating objects, so those need a boolean union or added `Intersection.BrepBrep` curves ([Rhino 8 help, Make2D](https://docs.mcneel.com/rhino/8/help/en-us/commands/make2d.htm)).

Curved surfaces need added linework, because the hidden-line computation returns only edges, creases, seams and silhouettes. The parameters object accepts curves as input geometry, so isocurves from `Surface.IsoCurve(direction, parameter)`, contours from `Brep.CreateContourCurves`, or `Brep.GetWireframe(density)` can pass through the same computation and land on a thin layer ([HiddenLineDrawingParameters API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.hiddenlinedrawingparameters); [Surface API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.surface); [Brep API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.brep)). **Unverified:** whether curves lying exactly on a surface come back as Visible, and the trim-aware variant `BrepFace.TrimAwareIsoCurve`, which was confirmed only through its use in the `rhinoscriptsyntax` source.

### Export is scriptable, but scale needs measuring

Vector PDF output goes through `Rhino.FileIO.FilePdf` with a `ViewCaptureSettings` object that carries `RasterMode`, `UsePrintWidths`, `WireThicknessScale`, `DefaultPrintWidthMillimeters`, `OutputColor` and `SetModelScaleToValue` ([ViewCaptureSettings API](https://developer.rhino3d.com/api/rhinocommon/rhino.display.viewcapturesettings); [FilePdf API](https://developer.rhino3d.com/api/rhinocommon/rhino.fileio.filepdf)). A January 2026 forum thread confirmed that `RasterMode = true` produced raster output that ignored layer print widths, and that setting it to false fixed this ([McNeel forum 214575](https://discourse.mcneel.com/t/lines-width-on-technical-pdf-scripting/214575)). **Unverified:** the API page describes `SetModelScaleToValue(double scale)` only as setting the model scale to a value, so whether 1:100 is passed as 100 or as its reciprocal is unknown. A skill should export once, read back `GetModelScale`, and measure a known length in the output before trusting scale.

SVG output uses `ViewCapture.CaptureToSvg(settings)`, shown in a 2019 example by Steve Baer of McNeel ([McNeel forum 79676](https://discourse.mcneel.com/t/export-svg-without-dialog-box/79676)). **Unverified:** no confirmed method for exact 1:1 or 1:N SVG output was found; a 2022 thread ended without a fix, and `doc.Export("x.svg")` on a headless document rescaled geometry by a factor of 60 in a 2025 report ([McNeel forum 145458](https://discourse.mcneel.com/t/exporting-an-svg-file-at-1-1-ratio-with-python/145458); [McNeel forum 201675](https://discourse.mcneel.com/t/svg-export-via-code-driven-file-io-specify-page-size-and-scale/201675)). DWG has an official Rhino 8 example using `FileDwgWriteOptions` and `doc.Export(path, options.ToDictionary())` ([Code-Driven File IO guide](https://developer.rhino3d.com/guides/rhinocommon/code-driven-file-io/)). **Inference:** because DWG export keeps geometry in model units, it is the safest exact-scale vector format of the three. **Unverified:** the option classes for DXF, SVG and AI export, since the `Rhino.FileIO` namespace page did not load during the research.

### Python 3 is the target engine, with four interop rules

Rhino 8 ships CPython 3.9.10 through Python.NET alongside IronPython 2, and Rhino 9 ships Python 3.13.13 ([Python 3 in Rhino guide](https://developer.rhino3d.com/guides/rhinopython/python-3-in-rhino)). A first line of `#! python 3` or a `.py3` extension selects the engine, and `# requirements: numpy` declares PyPI packages ([Scripting: Python guide](https://developer.rhino3d.com/guides/scripting/scripting-python/)). **Source conflict (minor):** the guide documents `#! python 3`, while McNeel's own samples write `# ! python3`; no page lists the accepted spellings ([SampleMake2dSnapshots.py](https://github.com/mcneel/rhino-developer-samples/blob/9/rhinopython/SampleMake2dSnapshots.py)).

Four rules prevent most engine errors. Enum members named `None` are reached as `.NONE` or with `getattr(Rhino.Geometry.SilhouetteType, 'None')`. A .NET `IEnumerable` return is an iterator and needs `list(...)` before indexing. `IEnumerable<T>` arguments are safest as typed collections such as `System.Array[Rhino.Geometry.Curve]`. Document access goes through `scriptcontext.doc` ([Python 3 in Rhino guide](https://developer.rhino3d.com/guides/rhinopython/python-3-in-rhino); [SampleCreateFromLoftRebuild.py](https://github.com/mcneel/rhino-developer-samples/blob/9/rhinopython/SampleCreateFromLoftRebuild.py)). **Inference:** .NET `out` parameters come back appended to the return value as a tuple, as the `rhinoscriptsyntax` source does with `surf, err = NurbsSurface.CreateNetworkSurface(...)`. The guide also notes that IronPython is faster for pure RhinoCommon calls, so heavy loops benefit from single batched calls or numpy ([Python 3 in Rhino guide](https://developer.rhino3d.com/guides/rhinopython/python-3-in-rhino)).

### Procedural richness can stay NURBS if it acts on control points

No official McNeel sample was found for noise, attractor fields, differential growth or marching cubes in Rhino Python, so the following is inference from the API list. Displacing `NurbsCurve.Points` or `NurbsSurface.Points`, or passing a displaced grid to `NurbsSurface.CreateFromPoints` or `CreateThroughPoints`, keeps the result as true NURBS. `Curve.CreateSoftEditCurve` and `Surface.CreateSoftEditSurface` are single-call attractor edits, and `Curve.CreateTweenCurves` gives morph sequences ([NurbsSurface API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.nurbssurface); [Curve API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.curve); [Surface API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.surface)). Growth and reaction-diffusion simulations produce polylines, grids or meshes, which become smooth geometry afterwards through periodic interpolated curves or the route `Mesh.QuadRemesh`, `SubD.CreateFromMesh`, `ToBrep()` ([SubD API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.subd); [SampleQuadRemesh.py](https://github.com/mcneel/rhino-developer-samples/blob/9/rhinopython/SampleQuadRemesh.py)). SubD is absent from the geometry types the hidden-line API lists as supported, so conversion to a brep comes before projection ([HiddenLineDrawingParameters API](https://developer.rhino3d.com/api/rhinocommon/rhino.geometry.hiddenlinedrawingparameters)).

In the build123d test, a loft through four periodic 12-point spline sections gave a valid solid, `project_to_viewport` returned 33 visible and 53 hidden edges in about 0.3 seconds, and `ExportDXF` wrote 78 SPLINE and 8 LINE entities on named layers ([PyPI build123d](https://pypi.org/project/build123d/)). build123d and CadQuery cannot share one Python environment at current versions, because build123d 0.13.0 requires OCP 8.0 and CadQuery 2.8.0 requires OCP 7.9 ([build123d package metadata](https://pypi.org/pypi/build123d/json); [cadquery package metadata](https://pypi.org/pypi/cadquery/2.8.0/json)). Raw OpenCascade through OCP also works, but OCP 8.0 removed the `TColgp_*` array classes that most older example code uses, which is a likely source of agent errors ([PyPI cadquery-ocp-novtk](https://pypi.org/project/cadquery-ocp-novtk/)). For self-review images, CairoSVG rendered every test SVG, and `ezdxf draw` rendered DXF directly ([PyPI CairoSVG](https://pypi.org/project/CairoSVG/); [ezdxf drawing add-on docs](https://ezdxf.readthedocs.io/en/stable/addons/drawing.html)).

**Inference:** the workable headless pipeline is build123d for geometry, sections and hidden-line edges, `ExportDXF` for SPLINE output, then ezdxf for hatches, extra layers, lineweights and sheet rendering. build123d already depends on ezdxf, so one install provides both. This stack is a fallback for machines without Rhino and a way to pre-compute geometry; it does not read or write Rhino's layer and print-width model.

### Fixed command sets give validity and remove expressiveness

Tools with a small fixed command set exist for both kernels. build123d-mcp (0.3.91) names the tools `execute`, `validate`, `compare`, `find_candidates`, `interface_features`, `edit_feature` and `install_skill`, and its README cites a CADGenBench result in which the same model rose from 0.360 to 0.457 with validity going from 88% to 100%; this figure is self-reported by the project ([build123d-mcp](https://github.com/pzfreo/build123d-mcp)). cadquery-mcp (0.1.0) offers `render`, `inspect`, `get_parameters` and `export` ([PyPI cadquery-mcp](https://pypi.org/project/cadquery-mcp/)). Zoo's hosted platform states in its own FAQ that production 2D drawings are still on its roadmap and that surface-heavy work is at an earlier stage ([Zoo FAQ](https://zoo.dev/docs/faq)).

The pattern across sources is that a closed tool vocabulary caps geometry at whatever the vocabulary contains. Text2BIM wraps BIM authoring in 26 high-level functions and reports most pass rates above 0.95, and its authors state that the toolset cannot produce irregular or curved models ([Text2BIM](https://arxiv.org/html/2408.08054)). EaseHee's standalone mode has about 246 tools and no surface tools ([PyPI rhino3dm-mcp](https://pypi.org/project/rhino3dm-mcp/)). The `rhinomcp` primitive list is the same effect. **Inference:** the useful form of a fixed command set for this task is a library of tested helper functions that scripts import, with the full RhinoCommon API still available underneath, and a fixed set of validation and export commands at the end of every script.

## Evidence favours verified examples, short scripts and numeric gates over visual self-review

Numbers in this section were extracted from the cited papers by an automated reader and should be spot-checked before reuse. Model names are given as the sources print them. Most 2026 items are arXiv preprints; peer-reviewed items are marked.

### Code is the right representation, and advanced operations remain the weak point

Executable Python CAD code is the representation most recent work converges on, because it can be run and checked and reuses the model's general coding ability; the peer-reviewed CAD-Coder paper (NeurIPS 2025) makes this argument for CadQuery ([CAD-Coder](https://arxiv.org/html/2505.19713v3)). The limits are specific. In Text2CAD-Bench, which allows three retries with error feedback, invalid output on the level that introduces sweeps, lofts and shells was 68% for GPT-5.2, 70% for Claude-4.5-Sonnet and 92% for Qwen3-max, with Gemini-3-Flash an outlier at 12.8%; on real-world parts it was 54% to 61% for the three models reported ([Text2CAD-Bench](https://arxiv.org/html/2605.18430v1)). In P3D-Bench, parameter errors (correct operation, wrong coordinates or operands) made up 54% to 55% of CadQuery failures in the harder settings, kernel failures 24% to 27%, and maximum reasoning effort lowered CadQuery validity for four of five models ([P3D-Bench](https://arxiv.org/html/2606.11152v2)). A November 2026 preprint that runs coding agents in FreeCAD reports Claude Code with Claude Opus 5.5 leading at 61.03% mean reward, and its abstract notes that a script that executes does not establish that the request was met ([Parametric CAD Bench v3](https://arxiv.org/abs/2611.02659)).

Direct coordinate output degrades with complexity. In SVGenius, Claude-3.7-Sonnet's perceptual accuracy fell from 80.25% on easy SVGs to 33.33% on hard ones as path and control-point counts rose ([SVGenius](https://arxiv.org/html/2506.03139v1)). Chat2SVG restricts its language model stage to simple shapes and adds curve detail by optimisation, citing the model's limits on geometrically complex paths ([Chat2SVG](https://arxiv.org/html/2411.16602v2)). **Inference, with no controlled comparison found:** an agent should compute curves from parameters and rules in code and should not type long coordinate lists.

### Six practices have measured support

| Technique | Measured effect | Source and grade |
|---|---|---|
| Verified API documentation and examples | Complex operations per asset rose from 1.20 to 5.86; errors fell from 3.29 to 2.43 | [LL3M](https://arxiv.org/html/2508.08228v1), preprint |
| Skill file with safe Rhino scripting patterns | Without it, all 10 ablation runs failed on calls to Rhino functions that do not exist | [MLLMto3D](https://www.mdpi.com/2075-5309/16/12/2437), peer-reviewed, single case study |
| Written decomposition before coding | Removing it cut visual question pass rate from 0.56 to 0.48 | [ShapeCraft](https://arxiv.org/html/2510.17603v1), preprint |
| Execution feedback loop | Script success rose from 53% to 85% in one annotation pipeline | [Text-to-CadQuery](https://arxiv.org/html/2505.06507v1), preprint |
| Executable tests written from the brief | About 10 points of pass rate over plain execution feedback; 93.8% agreement with human judgement against 47.4% for an image-based metric | [CADTests](https://arxiv.org/pdf/2605.07807), preprint |
| Kernel measurements plus renders to an independent judge | Median IoU rose from 0.8085 (single call) to 0.9629 | [CADSmith](https://arxiv.org/html/2603.26512), preprint |

The first two rows address the primitives problem most directly. Giving the model verified examples of complex operations increased how many it used, and a Rhino-specific skill removed invented function names. No source measures an instruction such as "avoid primitives" on its own.

Short scripts and staged build-up also have support. BlenderGym found that model edits stop reflecting the intended change in scripts longer than about 80 lines ([BlenderGym](https://arxiv.org/html/2504.01786v1)). Practitioner tools state the same rule: build one feature at a time, measure after important steps, and on failure retry a smaller step ([build123d-mcp](https://github.com/pzfreo/build123d-mcp)).

### Images are a secondary check

**Source conflict, reconcilable:** CADSmith found that removing renders from its judge raised mean Chamfer distance on complex parts from 1.42 to 49.68, while CADTests found that adding images to an agent loop left pass rate unchanged and greatly increased token use ([CADSmith](https://arxiv.org/html/2603.26512); [CADTests](https://arxiv.org/pdf/2605.07807)). The reading that fits both is that tests and measurements carry the gain wherever a requirement can be stated numerically, and a rendered view catches shapes that are structurally wrong while still satisfying the numbers.

Model self-assessment of drawings is unreliable. Zero-shot vision models deciding whether an orthographic drawing matches a render reached 0.52 to 0.67 accuracy, leaned towards answering yes, and did worst on top views ([Blueprint2CAD](https://arxiv.org/pdf/2611.02433)). In Blueprint-Bench, Claude Code asserted that every room in its floor plan was fully enclosed when that was false ([Blueprint-Bench](https://arxiv.org/html/2509.25229v1)). The peer-reviewed CADCodeVerify method (ICLR 2025) improves visual checking by generating two to five yes or no questions from the brief and feeding back only the failed ones; its vision model answered its own questions correctly about 65% to 68% of the time, and no gain appeared after the second refinement ([CADCodeVerify](https://arxiv.org/html/2410.05340v2)). ShapeCraft and Chat2SVG likewise saw returns flatten after two or three iterations ([ShapeCraft](https://arxiv.org/html/2510.17603v1); [Chat2SVG](https://arxiv.org/html/2411.16602v2)). Small gaps and unjoined parts passed both metrics and judges in CADSmith, and a practitioner test found a CadQuery union that dropped a cylinder at exact tangency while reporting a valid solid, exposed only by a volume check ([CADSmith](https://arxiv.org/html/2603.26512); [ModelRift](https://modelrift.com/blog/cadquery-vs-openscad/)).

### What has not been evaluated

No peer-reviewed or preprint study was found that evaluates an agent producing detailed 2D architectural plans or sections as vector linework with line weights, hatches and curved elements. Published architectural systems work at building-element or massing level. No study tests 2D-specific checks such as closed-loop tests, curve counts per layer or duplicate detection as agent feedback. Practitioner reports from the Rhino forum add that fine-detail judgement stays with the person and that complex tasks can take more iterations than manual work ([McNeel forum, October 2026](https://discourse.mcneel.com/t/rhino-ai-feedback-workflow-and-needed-features/223488); [McNeel forum, February 2026](https://discourse.mcneel.com/t/thoughts-on-openclaw-grasshopper-and-cad-agents-like-raven/215963)). Every rule transferred to drawings in the next section is therefore an extrapolation from 3D CAD, Blender and SVG work.

## The skill: a short workflow file, a verified cheat sheet and bundled validators

### Specification facts that constrain the design

A skill is a folder with a `SKILL.md` file whose YAML frontmatter needs a `name` and a `description`. Under the open specification the name is at most 64 characters of lowercase letters, digits and single hyphens and matches the folder name; Anthropic's platform rules also forbid the words "claude" and "anthropic" in it; the description is at most 1,024 characters ([agentskills.io specification](https://agentskills.io/specification); [Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). The description is the only text Claude sees when deciding whether to load the skill, and Claude Code truncates the combined `description` and `when_to_use` at 1,536 characters in its listing, so the main use case goes first ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). Anthropic's skill-creator notes that Claude tends to under-trigger skills and recommends a description that names concrete trigger terms ([skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)). For this skill those terms include section, plan, elevation, 2D drawing, Make2D, NURBS curve, hatch, lineweight, Rhino, RhinoCommon and rhinoscriptsyntax.

The body should stay under 500 lines and about 5,000 tokens, with detail in reference files one level below `SKILL.md`, each introduced with a condition for reading it ([Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)). After context compaction Claude Code re-attaches only the first 5,000 tokens of each invoked skill, which matters for long drawing sessions: the rules that cannot be skipped belong at the top ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). Personal skills live in `~/.claude/skills/<name>/SKILL.md` and reload live when edited. Skills created in the Claude app sync into `~/.claude/skills/synced/` as read-only copies on Claude Code 2.1.273 or later, so iteration is faster on a local working copy ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). **Source conflict:** Anthropic's platform overview says custom skills do not sync across surfaces, while the Claude Code documentation describes this one-way sync ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview); [Claude Code skills docs](https://code.claude.com/docs/en/skills)).

Three further points of official guidance shape the content. Bundled scripts are preferred over regenerated code for deterministic steps, and `${CLAUDE_SKILL_DIR}` in both the body and `allowed-tools` lets them run without a permission prompt ([Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [Claude Code skills docs](https://code.claude.com/docs/en/skills)). Explaining why a rule exists is recommended over capitalised commands, and a rule that must hold every time belongs in a hook ([skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator); [Claude Code skills docs](https://code.claude.com/docs/en/skills)). Environment-specific gotchas are described as the highest-value content and should sit in `SKILL.md` itself ([agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)). **Source conflict:** Anthropic's documentation says MCP tools should be written as `ServerName:tool_name`, while Claude Code was observed during the research to expose them as `mcp__server__tool`; which spelling a skill body should use in Claude Code is unconfirmed and needs a test in a fresh session ([Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

### Existing public skills leave this niche open

The most developed CAD skill read in full is the build123d `cad` skill from the text-to-cad project. It opens with a task routing table, runs each model and checks each change, and separates measurement from appearance: dimensions come from code, and snapshots show only arrangement. It also holds that a check is trusted only after it has been seen to fail ([text-to-cad cad skill](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/SKILL.md)). Two Grasshopper skills by Daniel Nunes Locatelli are built on the rule that a successful build proves compilation only, and the agent may not report completion until real solver output has been checked ([McNeel forum, Grasshopper plugin skills](https://discourse.mcneel.com/t/claude-code-writing-compiled-grasshopper-plugins-two-agent-skills/221307)). A `rhino3d-scripts` skill exists in GitHub's awesome-copilot collection, seen only in truncated form ([skills.sh listing](https://skills.sh/github/awesome-copilot/rhino3d-scripts)). No public skill for 2D architectural drawings or sections was found, and none of the Rhino skills inspected visibly contains a verified function cheat sheet. Among Anthropic's own skills, docx and pptx are the closest structural models: a short body, a routing table, a list of library traps, bundled validators and a required render-and-inspect step ([anthropics/skills docx](https://github.com/anthropics/skills/tree/main/skills/docx); [anthropics/skills pptx](https://github.com/anthropics/skills/tree/main/skills/pptx)).

### A proposed structure (inference from the findings above)

The top of `SKILL.md` should carry the standing rules, each with its reason. Geometry is produced only by scripts through the chosen route (`run_python` on the McNeel server, or `rhinocode script`), because typed primitive tools set the ceiling. Every script starts with `#! python 3` and reads document units and tolerance first, because one practitioner runbook names unit slips as the most common cause of bounding-box mismatches ([text-to-cad runbook](https://raw.githubusercontent.com/jettyio/agent-runbooks/main/runbooks/earthtojake/text-to-cad/cad/RUNBOOK.md)). Before any code, the agent writes a decomposition that names each non-primitive feature (which curves are blended, which surfaces are lofted or swept, where the cut planes are) and a parameter file that separates fixed dimensions from stylistic variables, following the ShapeCraft and MLLMto3D results. Any function outside the cheat sheet is looked up before use, because an invented name fails only inside Rhino and costs a full round trip. One script builds one component or one drawing layer, is run, validated and captured before the next is written. Repair is capped at three rounds per pass, changing the smallest responsible part, and remaining mismatches are reported.

A fixed script skeleton with one marked variable section keeps the fragile parts constant: header, imports, tolerance, layer setup, redraw control, then the geometry section, then validation, JSON report and capture. This borrows the fixed-versus-variable device from Anthropic's algorithmic-art skill ([anthropics/skills algorithmic-art](https://github.com/anthropics/skills/tree/main/skills/algorithmic-art)). Degrees of freedom follow fragility: low for setup, validation and export; medium for construction patterns supplied as parameterised helpers; high for composition.

The reference files would be a curves and surfaces cheat sheet, a sections and hidden-line cheat sheet, a layers and export cheat sheet, a drawing conventions file (layer names, plot weights, which segment classes go where), and worked examples taken from McNeel's samples. In line with the docx skill's approach, the cheat sheets should hold only what the model gets wrong: exact signatures, return quirks, wrapper traps such as those listed earlier, version tags, and names that do not exist. Each file over 100 lines needs a contents list at the top ([Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). A user's own notes on RhinoCommon pitfalls are the right seed for the gotchas list, since the guidance favours corrections from real tasks over general knowledge ([agentskills.io best practices](https://agentskills.io/skill-creation/best-practices)).

The scripts folder would hold a tested helper module (section and hatch, hidden-line to layers, isocurve density, export to PDF, SVG, DWG and PNG), a drawing validator, and a name checker that asserts every cheat-sheet name exists in the running Rhino. The validator translates the 3D evidence into drawing terms: every hatch boundary closed and planar, curve counts per layer against expectation, no duplicate or zero-length curves, bounding box against sheet size, solids valid before cutting, and a measured length against the intended scale. It writes JSON to a file and uses a non-zero exit code on failure. Visual review comes second: a capture at a fixed size of at least 1,400 pixels wide, since thin lines vanish at low raster sizes, examined with two to five yes or no questions derived from the brief. For final review, an independent subagent that sees measurements and images without the generator's reasoning follows the CADSmith design.

Evaluation should start before the skill is long. Anthropic's guidance is to build three test scenarios, record a baseline without the skill, and run each test in a fresh session, with about 20 should-trigger and should-not-trigger queries for the description ([Anthropic skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [agentskills.io optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)). **Source conflict:** the platform page says no built-in way to run evaluations exists, while the Claude Code documentation describes the skill-creator plugin with test cases, grading and A/B comparison ([Claude Code skills docs](https://code.claude.com/docs/en/skills)).

## Conclusion

The findings move the problem from prompting to tooling. The agent draws primitives because primitives are the cheapest valid action its tools offer, and the measured remedies all make complex operations cheaper and safer than they were: remove the typed shortcut, supply verified examples of lofts, blends and hidden-line calls, and attach a test that fails when the intended feature is missing. A drawing then behaves like a compiled artefact. The model is built in small scripts, sections and projections are computed from it, segment classes map to layers and plot weights, and export is one fixed command, so the agent's judgement is needed for composition and not for the mechanics that currently fail without notice.

The evidence base stops short of this exact use. Benchmarks cover mechanical parts, trail model releases by months, and say nothing about dense curved architectural linework, so the first hours of work on the skill are best spent on the verification table above and on a small personal evaluation set of three drawings scored with and without the skill. Those results will be the only direct evidence available for this task, and they will show quickly whether the weak joints (clipping planes in the hidden-line API, export scale, exact-scale SVG) need workarounds such as DWG as the primary exchange format.
